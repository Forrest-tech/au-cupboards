## 01 需求还原

去掉建筑行业包装，这是一套 **「图纸 → 计量柜选型清单」的两段式自动化流水线**，中间夹一个人工确认环节。

| 阶段 | 输入 | 输出 |
|---|---|---|
| STAGE 1 图纸 → 数字模型 | 建筑/户型图（DWG/PDF/Word/JPG） | 楼层数 + 每层 units 数量 |
| STAGE 2 库表 → 选型匹配 | 每层 units 数 | 计量柜库中所有可用柜型（1 种/2 种/3 种…）|
| STAGE 3 清单 → 导出 | 选型结果 | PDF / Word / JPG |

### 三个功能区

| 模块 | 核心交互 | 本质 |
|---|---|---|
| **A. 主工作台** | 左侧树导航 + 右侧工作区分两栏：左栏原样预览原始文档，右栏按楼层逐行展示选型结果 | 主从式（Master–Detail）布局 + 文档预览器 + 可编辑数据网格 |
| **B. 计量柜库入库** | 上传 DWG → 解析 → **先出分解预览** → 用户确认 → 入库 → 左按表计数量分类 / 右按排布形式展开（尺寸、介绍），支持编辑删除 | 「批量导入 + 人工校对」的字典编辑器 |
| **C. Building 管理** | 上传建筑图纸 → 预览 → 挂载到树的指定节点 → 自动解析楼层数与每层 units | 与模块 A 共用同一棵树、同一套预览器 |

### ✅ 需求里写得最好的两个决定

1. **模块 B 的「解析 → 预览 → 确认 → 入库」四步走** — 正是业界成熟做法。CAD 解析不可能一次到位，把人工确认放在入库前而非事后返工，是正确流程。
2. **模块 A 与 C 共用一棵树** — 避免楼栋文档与柜型库割裂，也避免重复实现导航。

## 02 柜型库 DWG 实图分析（新增 · 关键可行性证据）

> 你补充了 `Cold and hot water and gs meter cupboards detail 1.dwg` 在 AutoCAD 2024 中的实际截图。放大分析后，**这张图显著改变了几个技术判断** —— 好消息远多于坏消息。

### 2.1 从图中读到的确定事实

| 观察项 | 图中证据 | 对系统的意义 |
|---|---|---|
| **柜型以「矩形柜体 + 内部分格」构成** | 青色矩形 = 柜体外轮廓；内部红色矩形 = 每个表位的独立框；左上柜型为 **2 列 × 3 行 = 6 个表位** | 柜体识别可**纯几何化**：找闭合矩形轮廓 → 数内部子矩形个数 = 表位数。这**不需要 AI**，规则引擎即可 100% 准确完成 |
| **water / gas 表符号是独立可识别图元** | 每个表位内是白色管件+绿色表头的标准符号；**红色框 = gas 表**，**绿色竖线元素 = water 表管路** | water/gas 计数**可按图层 + 块名规则精确提取**。直接回答了 Q1 的歧义 —— 图纸本身就带语义，不需要推断 |
| **尺寸标注完整存在** | 左侧柜宽标注链：`50 / 175 / 200 / 100 / 250 / 175 / 50`，总宽 **1000**；右上柜标注 `50/150/400/150/400/150/400`，总高 **2200**、总宽 **1315**；下方柜 `50/120/130/50/400/100/150/100/150/50`，总宽 **1300** | **柜体尺寸可直接从 DWG 的 DIMENSION 实体读取**，无需按规范反算。Q10 答案：**读图纸标注**，规范公式仅作校验 |
| **柜型是多排布并列，而非多文件** | 同一张图内可见 **5 个以上**独立柜型（上方 2 个大柜 + 下方 3 个），每个下方都有一行细分格尺寸标注 | 证实 Q3 答案是**「一个 DWG 内用不同区域表示所有柜型」**。入库解析需按**空间聚类**切分柜型，而非遍历文件 |
| ⚠️ **命令行出现 `CAMS` 命令** | 命令行显示 `Command: CAMS` 及后续 `CAMS>>>` 交互提示 | **疑似已有 AutoCAD 插件/脚本在做这件事**（LISP 的 `(defun c:CAMS ...)` 或 ARX）。**必须查清** —— 若已存在，源码可直接复用或移植，能省掉整个 STAGE 2 的解析工作 |
| **存在多个同底图的小图** | 底部三个小图尺寸链各不相同 | 柜型库按**不同 units 数分组**组织，正是需求里「7 套 water+gas 有 4 种排布形式」的载体 |

### ✅ 重大利好：「100% 识别」这个死结，在柜型库这一侧基本解开了

报告 03 节判定「100% 识别不可兑现」，那个判断**只对建筑平面图成立，对柜型库 DWG 不成立**。理由：柜型是**规则几何图形**，有闭合矩形轮廓、有子矩形分格、有图层与颜色区分、有 DIMENSION 标注 —— 全都有确定的几何/语义锚点，不需要靠视觉猜。

这意味着 **模块 B（柜型入库 + 匹配）的准确率可以做得很高**，而真正的不确定性只集中在 **STAGE 1（从建筑平面图推断每层 units 数）**。项目的风险分布比原判断乐观得多 —— **建议把解析优先级从「建筑图 AI 识别」转移到「柜型库几何解析」**，后者才是第一天就能拿出成果的部分。

### 🔎 必须立刻查清的一件事：`CAMS` 是什么

截图命令行里 `CAMS` 是一个自定义命令（其后有交互式追问，形态像 AutoLISP 命令）。**如果这是你或团队已经写好的插件**，那么「DWG 解析」这件事你已经有现成实现了 —— 系统只需读取它的输出（实体表 / 属性字典 / 甚至导出 Excel/CSV），而不是从头做几何解析。

**请提供**：该 `CAMS` 命令的 LISP 源码或插件文件，以及它能输出什么。这可能把 P4 阶段从 10–14 人日降到 **2–3 人日** —— 目前**投入产出比最高的一个问题**。

### 2.2 修订后的解析策略

| | |
|---|---|
| ❌ **原方案：AI 视觉识别** | 把柜型图渲染成图片，用视觉模型数格子。精度不可控、不可复现、无法解释 |
| ✅ **新方案：纯几何 + 语义解析** | 在 DWG 实体层面直接解析：① 闭合多段线/LWPOLYLINE → 柜体外轮廓；② 其内闭合矩形 → 表位框，**数量即 units**；③ 按图层/块名区分 gas 表与 water 表；④ 读取 DIMENSION 实体 → 精确尺寸 |

### 🔧 数据模型调整：柜型增加「几何特征」字段

既然柜型可被完整几何描述，`CupboardVariant` 应新增一组可直接用于匹配与排版的字段：

```
layout_rows        : int     排布行数（如 3）
layout_cols        : int     排布列数（如 2）
positions_total    : int     表位总数（= units 数，如 6）
grid_aspect        : string  "2x3" / "1x7" / "2x2+3"
meter_spacing_h/v  : float   表位间距（从标注读出）
w / h / d (mm)     : float   柜体总尺寸（从 DIMENSION 读出，非手填）
bbox {x,y,w,h}     : float   原图定位，可回溯 DWG 坐标
source_sheet       : string  来源图号/布局名
```

有了 `layout_rows/cols`，需求里说的「每层 6 units → 3 种排布」就变成了**可枚举、可穷举**的匹配问题，而不是模糊判断。

### 2.3 「DWG 无法上传给我」的影响与应对

需要先厘清一个容易混淆的点：**系统最终是在你自己的电脑上运行的**，DWG 永远不需要传给我。它传不到我手上，只影响一件事 —— **我无法在写代码前用真实文件验证几何解析规则**。

| 维度 | 是否受影响 | 说明 |
|---|---|---|
| 系统能否解析真实 DWG | ✅ 不受影响 | 系统在用户机器上运行，读取本地文件。这是产品功能，不是开发依赖 |
| 能否交付可用的柜型库功能 | ✅ 不受影响 | 柜型库由用户在系统中上传 DWG 触发入库，流程不变 |
| 能否提前验证解析规则 | ❌ 受影响 | 只能从截图推断规则，无法确认不同柜型的边界是否有例外、是否有其他画法 |
| 工期估算的可靠性 | ⚠️ 略微受影响 | P4 基于截图推断，实际可能 ±30%。首次跑真实文件时可能需要一轮规则调优 |

> ⚠️ **这个约束带来的唯一实质风险：规则可能是「过拟合到这一张图」**
>
> 我看到的只是一张截图里的 2 个大柜 + 3 个小柜。真实 DWG 里可能有：非矩形柜体、异形表位、嵌套块、跨图框的柜型、不同标注体系（有的标 mm 有的标 m）。**如果把规则写死成「找闭合矩形 + 数内部矩形」，遇到例外图纸就会静默出错。**
>
> **应对：把解析器做成「规则可配置 + 首次运行有诊断输出」** —— 见 2.4。

### 2.4 因此对实现的三条硬约束

1. **解析规则必须外置为配置** —— 图层名、颜色、识别阈值、闭合判定容差全部放进 config 文件，不硬编码。用户遇到例外时改配置即可，无需改代码、无需找开发者。
2. **必须有「诊断模式」** —— 首次解析时输出诊断报告：识别到几个柜体、各识别到几个表位、哪些图元未被归类、置信度分布。让用户一眼看出哪里没对上，而不是拿到一堆错数据。
3. **修正字典是必需品，不是加分项** —— 用户每次手工修正块名↔表位数、图层↔表类型的对应关系，系统自动记住。**这是没有真实样本时唯一能保证准确率的机制。**

> 💡 **反过来看，这其实让「预览→确认」的价值更大了**
>
> 原本「预览确认」是为了减少返工。现在它多了一层意义：**它是让系统在没有预置知识的情况下自我校准的唯一手段**。用户在预览界面改几个框，系统下次就认得了 —— **第一个用这套系统的人付出的是校准成本，之后所有人享受校准后的准确率**。这也符合需求里「用户确认后入库」的原意，只是作用比原先更大。

## 03 可行性裁决：「100% 识别 DWG/PDF/JPG，不能有解析问题」

这是需求第 3 条，也是**整个项目唯一会导致失败的一条**。

> **结论：这条要求在工程上无法兑现，必须改写。**

不存在任何商业软件或开源库能对任意来源、任意版本、任意画法的建筑图纸做到 100% 无损解析。这不是水平问题，是**信息论层面的限制**：

- DWG 是 Autodesk 未公开的私有二进制格式
- 图纸里「哪条线是墙、哪个块是一套表计」没有任何强制标注标准 —— 图层名叫 `0`、`图层1` 还是 `WALL-FINAL`，全凭设计院习惯
- 行业公开工程共识：受控任务上 AI 视觉 85–95%，复杂图纸更低，且必须人工验证

### 各格式真实难度

| 格式 | 可行性 | 真实情况 | 应对策略 |
|---|---|---|---|
| **DWG** | 难点 | 私有闭源。高版本支持最好的只有 ODA（File Converter 免费需注册，SDK 收费）。LibreDWG 开源免费（GPLv3）但高版本支持不全、代理实体常丢失 | ODA → DXF → `ezdxf` 解析；LibreDWG 兜底；**必须校验代理实体是否转空** |
| **DXF** | 易 | 开放格式，`ezdxf`（MIT）完整支持 R12 → 最新版 | 直接解析 |
| **矢量 PDF** | 易 ✅实测已验证 | `pdfplumber`/`PyMuPDF` 可直接抽**矢量文字与坐标**。**✅ 已在 74 KEELER ST 实测确认：1.57 MB 完整文本层可抽，UNIT 标注直接可读（见 04 章）** | 优先抽文字层（`UNIT n`/`Apt 201`/`Type A`）。**⚠ 但实测发现「抽得到 ≠ 抽得全」，必须加缺号检测与置信度分诊** |
| **扫描 PDF / JPG** | 难点 | 纯位图。OCR 对小字、旋转文字、密集线网不可靠，只能走视觉模型 | ≥200 DPI → 视觉模型结构化抽取 → **强制人工确认** |
| **Word** | 中等 | 可解析，但拿不到几何信息 | 仅作为「单元数清单」的合法来源，不做图形识别 |

### 建议改写：从「100% 自动」改为「自动初稿 + 置信度 + 人工确认」

1. **每条解析结果带置信度** — 矢量文字命中=高；几何规则命中=中；视觉模型=低。低置信项高亮，要求人工裁定。
2. **人工修正沉淀为规则字典** — 每次改判记录「这个块名 = 4 套 water+gas」，系统越用越准。**这是真正的技术护城河**，也是唯一能逼近 100% 的路径。
3. **设「不可信」状态而非静默通过** — 解析不出来的楼层标为待处理，绝不猜数字填进去。工程数据里，一个错数字的代价远大于一个空格子。

**参考依据：** 调研中找到的同类商业产品 **BuildPass（澳洲本地）AI Floor Plan Scanner** 做的正是这件事 —— 上传 PDF 平面图，自动抽出 levels 和 rooms，**然后强制用户 review / rename / remove 后再 import**。它的产品形态本身就是对这个需求最好的回答。

### ✅ 补充：这条裁决已被真实图纸实测验证（见 04 章）

对 `74 KEELER ST`（35 页 A3 建筑图）的实测结果**支持这个改写方案**：矢量文本抽取**确实可行且质量很高**（不需要 AI 视觉），但**确实会漏数**（有缺号的楼层抽不全）。这正好说明 —— **问题从来不是「能不能抽」，而是「抽得全不全」**，而「抽得全不全」只能靠置信度 + 人工确认来保障，不能靠算法保证 100%。**本裁决在实测后依然成立，且更有说服力了。**

## 04 真实图纸实测：74 KEELER ST CARLINGFORD（新增 · 决定性数据）

> 你提供了真实项目图纸 `COMBINED ARCHITECTURAL DRAWINGS - 74 KEELER ST CARLINGFORD.pdf`（38 MB / 35 页 / A3 / Archicad 生成 / PDFTron 转换）。完整实测后，**结论比预期好，但也有一个必须处理的意外发现**。

### 4.1 图纸基本情况

| 项目 | 实测值 | 意义 |
|---|---|---|
| 页数 / 尺寸 | 35 页 / A3 横向 | 一个项目 = 一个多页 PDF，正是需求里说的「以 pdf 为主」 |
| 生成工具 | **Archicad**（GSPublisher）+ PDFTron | Archicad 生态，与 AutoCAD 不同，但 **输出的是标准矢量 PDF，文本层完整** |
| **矢量文本层** | **✅ 完整存在**（1.57 MB 可提取文本） | **这是最重要的好消息** —— 不需要 OCR，不需要视觉模型，`pdftotext` 直接就能拿到文字与坐标 |
| 图纸目录 | A000~A015 + A101~A107 + A201~A204 + A301~A304 + A401~A404，共 **35 张** | 有标准图纸编号体系，可作为楼层/图号的定位锚点 |
| 关键图纸 | **A008 UNIT SCHEDULE**（第 9 页） | 见 4.3 —— 这是整份图纸的「户数权威来源」 |
| 项目性质 | CO-LIVING HOUSING - S34，43 DOUBLE + 1 SINGLE，GFA 1,359.31 m²，FSR 1.43:1 | 澳洲 S34 住宅 + 合作居住形态，说明这类项目图纸确实高度规范化 |

> ✅ **决定性结论：STAGE 1 不需要 AI 视觉识别**
>
> 这份图纸有**完整矢量文本层**，楼层平面图上的 `UNIT 8`、`UNIT 9`、`KITCHEN`、`LIVING`、`BEDROOM` 全部是可选取的**真实文字对象（含精确坐标）**。这意味着 STAGE 1 的「每层 units 数」可以用**纯文本规则解析**完成 —— 准确率可预期、结果可复现、且能给出置信度。
>
> 原报告把建筑图识别归为「必须 AI + 人工确认」，**现在可以下调为「规则解析 + 置信度 + 边缘情况人工确认」**。这会显著改善工期与成本估算。

### 4.2 楼层与units 抽取实测结果

用 `pdftotext -layout` 逐页解析，页码定位完全可靠（图纸标题即锚点）：

| 页 | 图纸 | 抽取到的 UNIT 编号 | 数量 | 评价 |
|---|---|---|---|---|
| 17 | A101 BASEMENT | — | **0** | ✅ 正确，地下室无独立单元 |
| 18 | A102 GROUND | 2, 3, 4 | **3** | ❌ **偏少**，图上实际约 10 个（见 4.4） |
| 19 | A103 LEVEL 1 | 8, 9, 10, 11 | **4** | ⚠️ 连续编号，实际约 12 个 |
| 20 | A104 LEVEL 2 | 15, 16, 17, 18 | **4** | ⚠️ 同上 |
| 21 | A105 LEVEL 3 | 22, 23, 24 | **3** | ⚠️ 同上 |
| 22 | A106 LEVEL 4 | 28 | **1** | ❌ 明显偏少，图上有多户 |
| 23 | A107 ROOF | — | **0** | ✅ 正确 |

> ⚠️ **关键发现：纯文本抽取会「漏数」，这是必须处理的设计问题**
>
> 规律非常清晰：**连续编号被完整抓到（8-11、15-18 都是连号），但编号有断号的楼层就漏**。例如 LEVEL 1 抓到 8,9,10,11 是连号所以全中；而 GROUND 只抓到 2,3,4 就说明 UNIT 1 和 5+ 的标注文本**没有被提取到**。
>
> 换句话说：**「抓到几个编号」≠「这一层有几户」**。如果系统只靠数文本标注，会给出偏少的错误数字 —— **这在工程数据里是不可接受的，因为它看起来是个合理的数字，不容易被发现**。

### 4.3 意外发现：粉色填充 = 单元轮廓，但只在 A008 上

A008 UNIT SCHEDULE 页每层都有一张缩略平面图，**每个独立单元用粉色实心填充**。实测该填充色为 `RGB(255, 191, 191)` / `#FFBFBF`。这本来是最理想的识别信号，但：

| 位置 | 粉色填充 | 说明 |
|---|---|---|
| A008 UNIT SCHEDULE | ✅ 有 | 每层一张缩略图，粉色块 = 一个单元。这是**户数的权威视觉来源** |
| A102~A106 正式平面图 | ❌ 没有 | 实测粉色像素占比 **0.00%**，正式平面图里根本没有粉色 |
| PDF 对象层 | ❌ 不可提取 | pdfplumber 只能取到灰/白/蓝填充；**粉色不在标准 RGB 空间**，疑似 ICC/CMYK 色彩空间定义 |

> 💡 **结论：粉色是「可靠的交叉验证信号」，但不能作为主路径**
>
> 粉色填充无法从 PDF 对象层直接提取（需先渲染成位图才能取色），所以不应作为主识别路径。但它**可以作为一个高置信度的交叉校验源**：当文本解析给出「LEVEL 1 = 4 户」而粉色连通域给出「12 个」时，系统应当**自动标记为低置信度并弹窗提示用户复核** —— 而不是默默输出 4。
>
> 这正是「多信号交叉验证 + 置信度」机制的真实价值，现在有了具体实现路径。

### 4.4 两套编号体系并存 —— 必须显式处理

| 来源 | 编号样式 | 实测样例 | 问题 |
|---|---|---|---|
| 平面图（A102~A106） | **连续序号** | UNIT 2, 3, 4 / 8,9,10,11 / 28 | 同一层内唯一，但**跨层不连续**（GROUND 是 1-7，LEVEL 1 是 8-14…） |
| UNIT SCHEDULE（A008） | **楼层编码** | 101~111 / 201~209 / 301~309 / 401~403 | **首位即楼层号**，语义清晰，但与平面图对不上 |
| 文本层抓取 | 两套都出现了：`101/201/301/401`（表格）与 `UNIT 8`（平面图） | | |

> 🔧 **数据模型必须支持「编号体系」抽象**
>
> 不能把 unit number 存成单一字符串。建议拆成：
>
> ```
> Unit
> ├─ label          : "UNIT 8"          图上原始标注（照存，不解释）
> ├─ label_scheme   : "sequential" | "floor_encoded"
> ├─ seq            : 8                  连续序号（sequential 体系）
> ├─ floor_code     : 101                楼层编码（floor_encoded 体系）
> ├─ floor_ref      : → Floor (L1)       归属楼层
> └─ confidence     : 0.0~1.0            抽取置信度
> ```
>
> **关键设计：** `floor_code` 的首位可作为**楼层归属的强信号**（`2xx → LEVEL 2`）。当两套体系同时存在时，系统可以互相校验：若 `UNIT 28` 出现在 LEVEL 4 平面图，而 schedule 表里 4xx 有 3 户但平面图只抓到 1 个 UNIT 标注 → **触发低置信告警**。

### 4.5 实测暴露的其他工程细节（对开发有直接影响）

| 细节 | 实测情况 | 对开发的影响 |
|---|---|---|
| 📐 页面是 A3 横向，混合比例 | 平面图 1:400，场地分析 1:200 等 | 缩略图与正式图比例不同，**跨页比对尺寸必须先归一化到 mm**，不能直接用 PDF 点坐标 |
| 🏷️ 图纸编号是天然锚点 | A000~A015 / A101~A107 / A201~A204 / A301~A304 / A401~A404 | 解析时**优先用图纸编号定位页面**，比靠标题文字匹配稳健得多 |
| 📏 尺寸链完整可读 | 可提取 `10,200mm@ 2,000mm@ 4,000mm@` 这类链式标注 | **尺寸解析需处理千分位与 `@` 分隔符** |
| 🗂️ 一个 PDF 含全项目 | 35 页涵盖总图/平面/立面/剖面/详图/表 | 系统需支持"按图纸分类浏览"，不能把整份当单一文档处理 |

### 📌 实测结论汇总：三级置信度模型

| 信号 | 可靠性 | 用法 |
|---|---|---|
| **UNIT 编号连号完整** | **高** | 编号连续无断号 → 直接采信，高置信度 |
| **floor_code 前缀** | **高** | `2xx→LEVEL 2`，作为楼层归属的独立校验 |
| 粉色连通域计数 | 中 | 需渲染位图，成本高，但适合作为交叉校验兜底 |
| 户型特征词计数 | 中 | KITCHEN/LIVING/BEDROOM 出现次数可推断户数，作为辅助 |
| 视觉大模型 | 兜底 | 仅用于矢量文本层缺失的扫描件，**本图纸不需要** |

当高置信信号之间**互相矛盾**（如文本 4 户 vs 粉色 12 个），系统**必须弹窗要求人工裁定**，而不是选一个输出。

> ✅ **对工期的修正：STAGE 1 风险显著下降**
>
> 实测证明「楼层平面图 + UNIT 标注 + 完整文本层」这条主路径**是通的**。P3 从「AI 视觉识别 + 大量人工确认」调整为「规则解析 + 置信度分诊」，风险等级由 🔴 降为 🟡。**建议工期从 64–93 人日下调至 58–86 人日**，且 STAGE 1 的成功率预期大幅提高。
>
> 仍然存在的难点：**漏数问题**（文本层不全导致计数偏少）。这需要用「编号连续性检查 + 粉色交叉校验 + 人工确认」三重机制解决，属于工程可控范围。

## 05 补充一：有没有可直接套用的成熟系统框架？

这是个非常合理的诉求—— reinvent 别人的轮子没有意义。但调研后的结论需要分层说清楚：**「图纸→楼层清单」这一段没有成熟框架可直接套用；但「系统底座」和「单项解析能力」都有大量现成轮子可用。**

### 5.1 先纠正一个分类误区：三种「开源」不是一回事

讨论「有没有开源框架」时，最容易混淆的是下面三类东西。**它们的复用成本相差一到两个数量级**，必须分开评估：

| 层级 | 是什么 | 本项目对应的例子 | 复用成本 |
|---|---|---|---|
| **Tier A 函数库** | 只提供能力，不接管你的架构 | `ezdxf`、`pdfplumber`、`PyMuPDF`、`python-docx`、`LibreDWG` | ✅ **pip install 即用**，几小时到几天 |
| **Tier B 参考实现** | 完整应用源码，逻辑值得读、结构值得抄，代码不直接进仓库 | **OpenTakeoff**（量算+溯源+导出）、**BidWright**（装配体+数量表达式）、ERPNext CPQ（规则引擎） | ⚠ **读 1–2 天、设计上借鉴**，不引入依赖 |
| **Tier C 整系统底座** | 接管数据模型、权限、路由、任务队列乃至 UI | Frappe、NocoBase、Directus、ERPNext | ❌ **要么全盘接受其抽象，要么重写** |

> 💡 **本轮调研最重要的发现**：Tier B 这一层之前被完全忽略了，但它恰恰是本项目最该看的地方。Tier A 的库人人都会用，但 Tier B 里有两个项目**独立地解决了我方案里的核心难题，而且它们的解法互相印证** —— 这比「找到一个能直接套用的框架」更有价值。

### 5.2 逐项裁决：什么能套、什么不能套

| 需求环节 | 有无可直接套用的成熟框架 | 原因与替代方案 |
|---|---|---|
| **系统底座**（登录/权限/数据库/文件管理/后台任务） | ⚠ **有，但收益被高估** | Frappe / NocoBase 都能做，但**它们节省的 8–10 人日全在 CRUD 与权限上，而本项目的 UI 是强定制的主从式三栏布局 —— 这部分在所有底座里都要自建**。详见 5.4 |
| **STAGE 1：图纸 → 每层 units 数** | ❌ **无成品可套** | **但有高度对口的参考实现**：**OpenTakeoff**（Apache-2.0）已实现「打开图纸 → 量算 → 导出 + 全程溯源」，可直接读源码借鉴。业务语义（UNIT 编号体系、两套标签方案）仍须自研 |
| **STAGE 2：units 数 → 匹配柜型变体** | ⚠ **无成品，有可借鉴模型** | **BidWright** 的「参数化装配体 + 嵌套子装配 + 数量表达式」正是柜型变体的正确抽象；ERPNext CPQ 的 Super BOM + 条件规则是规则引擎范本。**都是 AGPL/GPL，不能直接引入** |
| **DWG 解析** | ❌ 无成品 | 没有任何开源/商业库能"读完 DWG 就得到业务语义"。**但底层转换有成熟轮子**：ODA File Converter（免费注册）→ DXF → `ezdxf`（MIT）。业务语义仍需自己写规则 |
| **PDF 矢量文字抽取** | ✅ **有，直接用** | 实测已证明 74 KEELER ST 文本层完整。`pdftotext -layout` / `pdfplumber` / `PyMuPDF` 都是成熟轮子，**零成本零 AI** |
| **扫描件/JPG 识别** | ❌ **无可靠自动方案** | 见 06 章：AECV-Bench 实测最强模型在「数门/数窗」上仅 **40–54%**。**注意：连最新的开源实现也放弃了这个思路** —— 见 5.3 的 OpenTakeoff |
| **Word 解析** | ✅ 有，直接用 | `python-docx`（MIT）读文字/表格；`docx-preview` 前端预览。都是稳定轮子 |
| **建筑/图纸版本管理**（Module C） | ❌ **不建议引入 DMS** | Mayan EDMS / Paperless-ngx / Alfresco / LogicalDOC 均为通用文档归档系统，**但我们需要的是「图纸挂到树节点 + 版本对比 + 解析任务关联」**。这是 10 张表的事，引入 DMS 等于多一个数据模型和一套认证要去适配 |
| **「每层 units 数」这个业务概念** | ❌ **没有任何框架有** | 这是澳洲计量柜业务的专有概念。BuildPass 有类似业务（PDF→levels/rooms→人工 review），但那是**商业产品不是可嵌入框架**。**这部分必须自研，是护城河所在** |
| **柜型库配置器** | ❌ 无成品 | ABN ecoreal 的 meter cabinet app 是最接近的，但也是商业产品。可以**照搬业务逻辑**（按表位数过滤→选排布→出 BOM），不能直接用代码 |

> ⚠ **关于「寻找并完整复刻一个成熟产品」的可行性判断**：需求第 4 条写「寻找一个成熟的商业产品并完整复刻」。调研 usBIM、Procore、Trimble Connect、BuildPass、ABN ecoreal 之后，**结论是：没有一个产品同时覆盖 STAGE 1（图纸→每层 units）+ STAGE 2（匹配柜型）+ 计量柜选型清单导出这条完整链路。**
>
> 最接近的三个产品各自缺一块：**BuildPass** 只做 STAGE 1（且是黑盒 SaaS）；**ABN ecoreal** 只做 STAGE 2（且只面向德国电网）；**usBIM/Procore** 做文档管理但不碰计量柜业务。**所以现实策略是「分模块照搬业务逻辑 + 自研中间层」，不是「复刻一个产品」。**

### 5.3 Tier B 深评：两个必须读源码的开源项目

这两个项目不是「可以直接套用的框架」，而是**「已经独立解决了我们最难的那部分问题」的参考实现**。认真读它们的代码，能省掉至少一周的方案推敲。

#### ① OpenTakeoff —— 最接近 STAGE 1 的开源实现（Apache-2.0）

2026 年 7 月开源的浏览器端工程量算引擎（Kentucky AI，135 star），定位是「打开一张建筑平面图，量出工程量」。**它的功能列表与本项目 STAGE 1 高度重合：**

| 它的能力 | 对本项目的意义 |
|---|---|
| 浏览器内直接打开 PDF 图纸，**零上传、零服务端** | 与我们的「本地部署 + 文件不出机器」约束完全一致。**可验证「纯前端图纸交互」这条路走得通** |
| 比例自动校准（公制 1:50 / 1:100） | 我们做尺寸与净距校验时必需的能力，现成实现可参考 |
| One-Click Area：**在填充图案上自动描出房间轮廓** | **这是关键。** 见下方「重要旁证」 |
| Count 模式（计数）、面积、线性、周长、体积 | 计数即我们要的 units 数；面积/线性可支撑未来的柜体表面积计算 |
| **Provenance（溯源）：每一个测量都记录比例、怎么测的（自动/手绘）、谁测的（人或 AI）** | **独立印证了我方案里「修正字典 + 置信度分诊」的设计。** 它把「这个数字怎么来的」当成一等公民，而不是事后补 log |
| 导出 CSV / JSON / Excel / **带标注的图纸 PDF** | 导出格式可直接对齐需求里的 PDF/Excel 清单 |
| 支持整套图纸（plan set）：图册、**标题栏文字**、页面渲染 | **标题栏文字**正是我们识别图号与楼层名的可靠来源之一 |
| 附带 **MCP server**，AI Agent 可驱动同一套引擎并审计结果 | 提供了「AI 只做兜底、结果必须能被程序复核」的工程范式，与我们 06 章结论一致 |

> ✅ **重要旁证：两个独立来源得出同一个结论**
>
> **06 章的 AECV-Bench 实测结论是「视觉模型数符号不可靠，最强只有 40–54%，必须走文字/几何规则」。而 OpenTakeoff 这个 2026 年 7 月的最新开源实现，在「自动识别房间/单元」上选择的也不是视觉模型，而是基于填充图案的**连通域填充（flood fill）** —— 也就是几何算法。**
>
> 两个来源、方法完全不同、结论一致：**建筑图纸的自动计数应走几何与文本规则，AI 视觉只做兜底和异常提示。** 这条交叉验证显著提升了我方技术路线的置信度，也说明我们方案里「粉色连通域分析」的方向是对的。
>
> **动作项：把 OpenTakeoff 加入必读清单，半天读完它的 count 模式与 provenance 结构。**

#### ② BidWright —— 最接近 STAGE 2/3 的开源实现（AGPL-3.0）

2026 年 3 月建库的 AI 原生工程估算平台（TypeScript，约 57 star，活跃维护中）。**它的数据模型正是柜型选型该用的形状：**

| 它的模型 | 对应本项目的什么 |
|---|---|
| **参数化装配体（Parameterized assembly）** | 一个柜型变体 = 一个装配体模板 |
| **嵌套子装配体**（sub-assemblies） | 柜体本体 + 每个表位子组件 + 门/锁/支架，**正好对应我们 `positions_total` 与 `layout_rows/cols` 的组合结构** |
| **数量表达式**（quantity expressions） | 「2 行 × 3 列 = 6 表位」这类**可计算而非硬编码**的排布表达 |
| 2D PDF 量算结果**直接挂到报价行项**（worksheet line items） | 我们的「楼层行 × 柜型」矩阵 —— **连交互形态都一样** |
| 报价评审带**证据链**（evidence tracking） | 我们的置信度分诊 + 人工修正记录 |
| 多 LLM 供应商编排 + 本地 Ollama 向量 + pgvector | 说明这类系统的 AI 组件确实是**可插拔的多供应商层**，不是单点依赖 |

> 🚫 **BidWright 为什么不能直接引入**：**AGPL-3.0** 是比 GPL 更严格的传染性许可：即使只通过网络提供服务，也必须向使用者提供完整源码。本项目是**要商业交付给澳洲客户的私有系统**，直接引入 AGPL 代码在合规上不可行。**正确用法是：读它的数据模型与交互设计，自己实现。**

### 5.4 可选底座：Frappe vs NocoBase vs 从零搭（修正版）

> ⚠ **本节修正了上一版报告的一处错误结论**
>
> 上一版写「Frappe 是 GPLv3，存在传染性风险」，**这是错的**。经核实（GitHub 仓库 License badge 与官方文档）：**Frappe Framework 本身是 MIT 许可**；**GPLv3 是 ERPNext 这个上层应用**的许可。两者是不同的项目，只用 Frappe Framework 不触发 copyleft。**因此「许可风险」这一项应从 Frappe 的劣势中移除。**
>
> 另一处也需要更新：**Frappe v15 已支持 PostgreSQL，但仍标注为实验性**，官方与维护者均明确「生产环境仍推荐 MariaDB」。所以「完全不支持 PostgreSQL」的说法也需修正为「可跑但不建议用于生产」。

| 维度 | Frappe Framework | NocoBase | 从零搭（FastAPI + React） |
|---|---|---|---|
| 许可 | ✅ **MIT**（仅 ERPNext 为 GPLv3） | ✅ **Apache-2.0**（2026-02 由 AGPLv3 改版） | ✅ 自选，无约束 |
| 技术栈契合度 | ✅ Python，与解析层同语言 | ⚠ Node.js/React，解析层需跨语言 | ✅ Python + React，完全可控 |
| 数据库 | ⚠ MariaDB 为主；PG 实验性 | ✅ PG / MySQL / SQLite | ✅ SQLite 起步，可后迁 |
| 主从式三栏 UI | ❌ Desk 不适合，须自建前端 | ❌ 页面块虽可拼，但达不到要求 | ⚠ 全自建，但完全可控 |
| CAD/PDF 原样预览 | ❌ 须自建 | ❌ 须自建 | ⚠ 须自建 |
| 规则引擎/配置器 | ⚠ 需自研或引 CPQ | ⚠ 需自研 | ⚠ 自研，但可控 |
| 可视化工作流 | ✅ 内置 | ✅ 7 类触发 + 24 类动作节点 | ❌ 自研 |
| 学习曲线 | ❌ 陡（DocType 元数据范式） | ⚠ 中（插件微内核） | ✅ 无 |
| 隐性成本 | ❌ 生态锁定，迁出痛苦 | ❌ 社区版阉割（SSO/高级工作流在商业版） | ⚠ 权限/审计/队列全自写 |

> ✅ **底座裁决：仍然推荐从零搭，但理由变了**
>
> 上一版给 Frappe 开的「省 8–10 人日」在修正后仍然成立，但**这笔省下的时间恰好是本项目不需要的时间**：它省的是 CRUD、表单、权限矩阵 —— 而我们的前端 100% 是三栏主从式自定义布局 + CAD/PDF 原样预览 + 楼层×柜型矩阵，这些在任何底座里都是自建。**换来的是 DocType 范式学习成本、生态锁定、以及为了用它的 REST 层而不得不用它的前端构建方式。**
>
> **因此：P0 用 FastAPI + SQLModel + SQLite 自己搭，但把「权限模型」和「审计日志」两个模块从第一天就设计成可替换的独立层** —— 这样未来若团队规模变大、或客户要求多租户，替换底座的成本可控。
>
> **唯一例外情形：若客户明确要求「开箱即用的多租户 SaaS」或「强审计合规」，则改用 NocoBase**（Apache-2.0 + PG 支持，比 Frappe 更契合本项目，且许可最干净）。

### 5.5 解析任务队列：Celery vs Temporal（附带裁决）

「上传图纸 → 异步解析 → 人工复核 → 入库」是一条带人工等待的长流程，有人会想到引入 Temporal。这里给出明确裁决，避免过度设计：

| 方案 | 优势 | 对本项目的判断 |
|---|---|---|
| **asyncio worker + DB 状态机**（原方案） | 零依赖、单进程够用、状态可查 | ✅ **推荐。** 单机部署、任务时长分钟级、无跨服务分布式需求 |
| **Celery + Redis** | 生态成熟、Python 原生、可水平扩展 | ⚠ 单机场景属于过度设计；若未来要 P0 多项目并行再引入 |
| **Temporal** | 持久化执行、跨天跨服务、人工审批原生支持 | ❌ **不引入。** 它的价值在于「跨天、跨服务、故障后精确恢复」，本项目单机部署无此需求，引入只会增加运维面和学习成本 |
| **Camunda（社区版）** | BPMN 2.0 可视化建模 | ❌ **不引入。** BPMN 对「解析→复核→入库」这种四步流程是杀鸡用牛刀 |

**但有一点值得借鉴**：无论用哪个队列，**任务状态必须显式建模并可查询**（`queued / running / needs_review / confirmed / failed`），而不是靠日志推断。这正是 OpenTakeoff 把 provenance 作为一等公民的同一个道理。

### 5.6 为什么不建议引入 DMS / BIM 平台

| 候选 | 许可 | 不采用的理由 |
|---|---|---|
| Mayan EDMS | Apache-2.0 | 自动化与分类能力不错，但**没有真实的版本历史**（是「标签 + 工作流」模型），与我们要的「图纸 v1/v2 差异对比」正相反 |
| Paperless-ngx | GPLv3 | 面向扫描件归档与消费级标签管理，不适合工程图纸 |
| Alfresco Community | LGPLv3 | 企业级 records management，配置成本极高，与单机部署诉求背道而驰 |
| Kimios | LGPL | **headless（无 UI）**，适合做后端服务但需自建全部界面；本项目只需 10 张表，不值当 |
| OpenProject | GPLv3 | **专为 BIM workflows 设计，值得作为流程设计参考**，但它是项目管理工具（甘特图、看板），不解决选型与解析 |
| Speckle | Apache-2.0 + EE 条款 | **AEC 数据平台，设计质量高但方向不符**：面向 Revit/IFC 三维模型协同，不是 PDF/DWG 图纸解析。**值得借鉴**的是它的**内容寻址版本模型**（commit→version、branch→model）—— 可用于我们的 Drawing 版本设计。**注意其许可陷阱**：`workspaces` 与 `gatekeeper` 两个模块（135 个 TS 文件）属 Speckle 企业版许可，禁止 copy/merge/distribute |

> 💡 **Module C 的正确做法**：「图纸版本管理」在需求里看着像 DMS，实际上它的本质是**我们自己的业务实体**：`Drawing`（文件哈希、图号、标题栏文字、页数）+ `DrawingVersion`（版本号、上传人、变更说明）+ `Building` 树节点挂载关系 + `ParseJob` 关联。**4 张表 + 一点乐观锁即可，约 3–5 人日。** 引入任何外部 DMS 都会多出一个数据模型、一套认证和一套权限需要适配，收益为负。

### 5.7 最终推荐：混合架构

| 环节 | 选型 | 说明 |
|---|---|---|
| 底座 | 自建轻量后端 | FastAPI + SQLAlchemy + SQLite（保留许可自由与架构自由，权限/审计层做成可替换模块） |
| 轮子 1：DWG → DXF | ODA File Converter | 外部进程，免费注册 —— 不自己写解析器 |
| 轮子 2：DXF 实体解析 | `ezdxf`（MIT） | 社区活跃、文档完整、Python 原生 |
| 轮子 3：PDF 文字抽取 | `pdfplumber` / `PyMuPDF` / `pdftotext` | 实测已验证 |
| 轮子 4：扫描件/位图 | **降级为兜底**：VLM API | 见 06 章，因实测精度不足 |
| 轮子 5：DWG 预览 | `mlightcad/cad-viewer`（MIT） | WASM 浏览器端 |
| 参考实现 | OpenTakeoff / BidWright | **读源码借鉴设计，不引入代码**（见 5.3） |

> ✅ **结论：没有「能直接套用的开源系统」，但有三层可复用的东西**
>
> **① 可以直接依赖的库（Tier A）：**`ezdxf`（DWG 实体）、`pdfplumber`/`PyMuPDF`（PDF 文字）、`mlightcad/cad-viewer`（DWG 预览）、`python-docx`（Word）、`LibreDWG`（兜底）。**另加一项**：`Shapely`（几何运算，用于连通域与面积计算）、`DuckDB`（对 74 KEELER ST 这类 1.57 MB 提取文本做结构化查询与分析，零运维单文件）。这些是**成熟、可直接依赖、不需要自己造**的。
>
> **② 必须读源码借鉴的参考实现（Tier B）：****OpenTakeoff**（STAGE 1 的量算 + 溯源 + 导出结构）、**BidWright**（STAGE 2/3 的装配体与数量表达式）、ERPNext CPQ（规则引擎范式）。**这三个能省约 5–8 人日的方案推敲，但代码不进仓库（AGPL/GPL 或架构不符）。**
>
> **③ 必须自研的（约 25–35 人日）：**① 「每层 units 数」的业务抽取逻辑（含漏数检测与置信度分诊）；② 柜型库的几何分解规则 + 诊断模式；③ `label_scheme` 编号体系抽象；④ 选型匹配与澳洲规范尺寸校验引擎。**这四项恰好构成系统的核心竞争力 —— 这也印证了需求方坚持「自研而非复刻」是正确判断。**
>
> **④ 关于系统底座（Tier C）：修正许可误判后仍不推荐 Frappe/NocoBase**，理由不是许可，而是「省下的都是我们不需要的 UI 时间，换来的是范式学习与生态锁定」。**把权限与审计做成可替换层，即可保留未来换底座的自由。**

## 06 补充二：解析算法与 AI API 的选型（含实测精度数据）

这个补充问得非常对 —— **04 章的实测已经证明 STAGE 1 不需要 AI**，但我们仍需要一个明确的「什么场景该用什么算法」的决策表，以及各方案的真实精度。

### 6.1 核心数据：AI 在建筑图纸上的真实精度（AECV-Bench 2026）

> ⚠ **这是本次调研最重要的发现，直接决定架构走向**
>
> **AECV-Bench（UNSW 出品，2026 年 6 月更新，12 个模型）**专门测多模态模型在真实建筑/工程图纸上的能力，结论非常清晰：**模型「读得懂文字」但「数不准东西」。**
>
> - **OCR / 文字抽取 ≈ 95–98%**（房间名、尺寸标注、注释）—— 很强
> - **符号计数（数门/数窗/数卧室/数厕所）= 40–54%** —— 不可用
> - **空间推理 = 0.54–0.88** —— 中等，且模型间差异大
>
> **对本项目的直接含义：** 「每层有几个 unit」本质上是**符号计数**问题。**直接问 AI「这层有几套单元」会得到 40–50% 正确率 —— 在工程数据里这是灾难性的**，因为它会给出一个看起来合理的错误数字。所以 **AI 绝不能作为 STAGE 1 的主路径**，这与 04 章实测「纯文本抽取才是正道」完全一致，互为印证。

#### AECV-Bench 符号计数实测排名（Exact Match Accuracy，越高越好）

| 模型 | 总分 | 卧室 | 门 | 厕所 | 窗 | 结论 |
|---|---|---|---|---|---|---|
| Gemini 3.5 Flash `Google` | 0.54 | 0.93 | 0.43 | 0.82 | 0.39 | 最强也只有 54% |
| Claude Fable 5 `Anthropic` | 0.52 | 0.93 | 0.36 | 0.82 | 0.29 | |
| GPT-5.5 `OpenAI` | 0.48 | 0.93 | 0.30 | 0.77 | 0.28 | |
| MiniMax M3 `开源` | 0.47 | 0.92 | 0.23 | 0.84 | 0.17 | 最佳开源仅 47% |
| Qwen 3.7 Plus `开源` | 0.46 | 0.89 | 0.16 | 0.84 | 0.14 | |
| GLM-4.6V `开源` | 0.39 | 0.79 | 0.09 | 0.82 | 0.03 | |

> 💡 **一个很关键的规律：卧室识别很高，门/窗很低**
>
> 所有模型的**卧室准确率都在 0.79–0.93**（因为卧室通常有明确的文字标注「BEDROOM 2」和固定位置），但**门只有 0.09–0.43、窗只有 0.03–0.39**（门是弧线符号、窗是图形符号，无文字锚点，模型只能「看图猜」）。
>
> **这印证了一条关键工程原则：** 凡是**有文字锚点**的识别任务（UNIT 8、KITCHEN、BEDROOM、尺寸链）→ 文字层抽取就能做到 95%+；凡是**纯图形符号**的识别任务（数门、数窗）→ 连最强 AI 都不可靠。**所以 STAGE 1 应该只依赖前者，完全避开后者。** 这与 04 章「文本抽取 + 缺号检测」的方案完全一致。

### 6.4 关键判断：STAGE 1 的准确度其实不依赖 AI

> ✅ **准确度的真正来源（回应「需要保证准确度」的核心诉求）**
>
> 需求方最关心「保证准确度」。结合本次调研，准确度的来源按贡献排序是：
>
> 1. **矢量文本层（免费，95–98%）** —— 主路径。UNIT 标注、房间名、尺寸链都有文字锚点，可靠。这是准确度的**主要贡献者**。
> 2. **缺号检测 + 交叉验证（免费，100% 可靠）** —— 这是本系统的**核心创新**。04 章实测「文本抽全会漏数」，而 A008 粉色连通域 + 单元表 `floor_code` + 封面声明可以互相校验。**三信号不一致就强制人工确认 —— 这比任何 AI 都可靠，因为它不猜测。**
> 3. **A008 粉色填充位图分析（免费，90%+）** —— 仅在 A008 页面运行，作为户数权威视觉来源。
> 4. **VLM API（付费，40–54% 计数）** —— **仅用于无文本层扫描件的兜底**，且强制人工确认。**不指望它做主要识别。**
> 5. **修正字典（免费，越用越准）** —— 每次人工改判沉淀为规则，系统自我校准。复利资产。
>
> **结论：准确度不来自「更强的 AI」，而来自「多信号交叉验证 + 人工兜底 + 自我校准」的机制设计。** 这正是 BuildPass（澳洲同类产品）验证过的产品形态 —— **AI 出初稿 + 人工 review 后入库**，而不是「AI 全自动」。

## 08 技术选型

### 8.1 DWG 解析：四条路硬对比

| 方案 | 费用 | 高版本 DWG | 代理实体 | 结论 |
|---|---|---|---|---|

### 💡 决定性发现：浏览器里已经能直接看 DWG

开源项目 **`mlightcad/cad-viewer`（MIT）** 通过 WebAssembly 在**纯浏览器、无后端**环境解析并渲染 DWG/DXF：

- 60+ FPS，支持图层控制、Paper Space、填充图案、测量、批注
- **自带 PDF / SVG / 自包含 HTML 导出插件**
- 直接解决需求 1 的「左侧原样显示 DWG」和「导出 jpg/pdf」，**预览层不需要写任何 CAD 解析代码**

备选 `@x-viewer/core`。注意其架构文档也明确指出：最好用的 DWG 解析器其实是 ODA —— 与 8.1 结论一致。

### 核心数据模型

```
Building  1─n Floor  1─n Unit
   │           │
   │           └─ n:m ─ CupboardInstance ──→ CupboardVariant
   │                                                  │
   └─ n ─ Document (DWG/PDF/Word/JPG)          CupboardType
        ├─ id, 原文件路径, 版本, SHA256              └─ water_meter_count
        ├─ 图纸类型/来源（建筑/给排水/电气）              └─ gas_meter_count
        ├─ 图纸号 sheet_no（A1xx/A3xx…）              └─ 计量位布局描述
        └─ 缩略图 / 预渲染缓存

Unit（🆕 因实测新增 —— 必须支持两套编号体系，见 04 章）
  ├─ label          : "UNIT 8"          图上原始标注（照存，不解释）
  ├─ label_scheme   : "sequential" | "floor_encoded"
  ├─ seq            : 8                  连续序号
  ├─ floor_code     : 101                楼层编码（101/201/301…）
  ├─ floor_ref      : → Floor (L1)       归属楼层
  └─ confidence     : 0.0~1.0            抽取置信度

CupboardVariant（排布形式）
  ├─ layout_code            如 4A / 4B / 4C（7套表可有4种排布）
  ├─ positions_total        表位总数（= units 数）  ← 数子矩形得到
  ├─ layout_rows / layout_cols   排布行列             ← 可穷举匹配
  ├─ grid_aspect            "2x3" / "1x7" / "2x2+3"
  ├─ w / h / d (mm)         柜体尺寸  ← 从 DIMENSION 实体读取，非手填
  ├─ meter_spacing_h/v      表位间距
  ├─ arrangement_desc       排布文字描述（1×4 / 2×2 / 2+3+2 …）
  ├─ thumbnail_svg / 缩略图
  └─ source_doc_id + 源图框名 + bbox{x,y,w,h}   ← 可溯源回 DWG 原位置

ParseJob
  ├─ status        queued/parsing/needs_review/confirmed/failed
  ├─ confidence    每项结果独立置信度
  ├─ raw_result    原始识别输出（可复现、可审计）
  ├─ multi_signals 各信号独立结果（文本/粉色/关键词），用于交叉验证
  └─ corrections   人工修正记录 → 沉淀为 block_name → meter_count 规则字典
```

### 🔑 数据模型里最关键的两个设计

1. **`CupboardVariant` 必须存 `source_doc_id + 源图框名`** — 任何柜型都能一键跳回 DWG 原位置，用户才敢用系统给出的尺寸。
2. **`ParseJob.corrections` 是整个系统的复利资产** — 每次人工改判都变成一条规则，识别准确率随使用单调上升。这是把"100% 识别"这个不可能目标，转成"越用越准"这个可达成工程目标的关键机制。
3. **`ParseJob.multi_signals` 是应对"漏数"的唯一手段**（🆕 因实测新增）— 04 章实测证明纯文本抽取会漏数（LEVEL 4 只读到 1 间）。必须把文本、粉色连通域、关键词计数三路信号**分别记录**，而不是只存一个最终数字。只有这样才能在信号冲突时报警，而不是静默输出一个偏小的错数。
4. **`Unit.label_scheme` 不可省略**（🆕 因实测新增）— 平面图用连续序号、单元表用楼层编码，两套体系并存且互相对不上。存成单一字符串会导致跨项目匹配全错。

## 10 核心难点与解法

| 难度 | 难点 | 解法 |
|---|---|---|
🟡 **最难（已实测，降级）** | 每层 units 数量识别 | **已在 74 KEELER ST 实测**：矢量文本层完整可抽，UNIT 标注直接可读，**不需要 AI**。但**会漏数** —— 连续编号段抽全、有缺号的楼层漏抽（LEVEL 4 只读到 1 间）。**解法是三路信号交叉验证**：① 文本 UNIT 编号连续性 ② 房间关键词计数 ③ 粉红填充连通域（仅 A008 有）。**柜型库侧的几何确定性无法复用到建筑平面图** —— 建筑图没有闭合矩形网格 |
🔴 难点（范围已缩小） | DWG 代理实体丢失 | 转换后完整性校验：转换前后实体数/块数对比，差异超阈值直接告警，不静默通过。**注：74 KEELER ST 是 PDF 出图，无此风险；风险仅来自业主直接提供的建筑 DWG** |
**已降级**（原「较难」） | 柜型自动分解入库 | 柜体是规则闭合矩形 + 内部子矩形分格，**几何解析即可，不必用 AI**。数子矩形个数 = units 数，按图层区分 water/gas，读 DIMENSION 取尺寸。风险大幅下降 |
**已降级**（原「中等」） | 选型匹配算法 | 有了 `layout_rows/cols/positions_total`，匹配变成**有限组合穷举**：某层 units=N → 找出所有满足 positions_total=N 的柜型（含 2×N1+N2 组合）。纯查表，无歧义 |
**已降级**（原「较难」） | 楼层顺序与命名 | 实测命名是 `BASEMENT / GROUND / LEVEL 1–4 / ROOF` —— 已是主流规范，**归一化映射表一次写对即可**。真正要处理的只有地下层无 units 的跳过规则 |
🆕 中等 | **两套编号体系并存** | 平面图用连续序号（2–28），A008 单元表用楼层编码（101/201/301/401）。**不能混为一谈**，需在 `Unit` 模型里分存 `seq` 与 `floor_code`，并以图号（A102→LEVEL 1）作为楼层锚点交叉校验 |
🆕 中等 | **多图纸集与多比例** | 单项目 PDF 常有 30+ 张图、混合 A3/A4 比例、含封面/目录/透视图。**必须靠图号前缀过滤**（A1xx 平面 / A3xx 立面 / A4xx 剖面），否则会把立面图上的"层号"误当楼层 |
中等 | 原样预览一致性 | CAD 图纸存在 SHX 字体缺失、线型缺失问题，需字体映射表与线型兜底。**PDF 侧实测无此问题**（Archicad 出图，字体已嵌入） |

## 13 待澄清问题（开工前必须确认）

**Q1 「units」到底指什么？** ✅ 已基本解答 — 从柜型库截图看，**一个表位 = 1 套 water + gas（冷热双表 + 1 气表）**，所以在这套库里 units ≈ 表位数。真实图纸实测进一步支持这个口径：**每个 UNIT 标注对应一套独立计量柜位**，单元表（A008）的表位数与平面图上的 UNIT 数应当一一对应。

> **剩余唯一需你确认的：** ① 图纸封面上除43 套 double + 1 套 single 之外，还有 **2 处 CO-LIVING communal 共享区（S34）** —— 这些是否也要配柜、是否计入 units？**②** 是否有「1 个 unit 配 2 个柜位」或「2 个 unit 共享 1 套表」的情况？

**Q2 每层 units 数据来源是什么图？** ✅ 已解答 — **已确认为建筑平面图，且实测给出了完整答案。**

- **① 主路径 — A1xx 平面图上的 `UNIT n` 文字标注**。74 KEELER ST 里 LEVEL 1 图上清晰可读 `UNIT 8 / 9 / 10 / 11`，同页还有 `ND.76-72 KEELER ST` 可作地址锚点。**矢量文本层完整可抽**（`pdftotext -layout` 抽出 1.57 MB 文本），无需 AI。
- **② 辅助 — A008 单元表**（专有粉红填充标每套单元），是全项目里唯一的"按单元着色"页面。
- **③ 校验 — 房间关键词计数**（KITCHEN / LIVING / BED / BATH / BALCONY 等）。

> ⚠ **实测发现的坑：单靠文本会漏数。** 连续编号段能抽全，但有缺号的楼层会漏（LEVEL 4 只读到 1 间）。所以不能只做文本抽取，**必须做三信号交叉验证 + 置信度分诊**（详见 4.2 / 4.5）。

**Q2b 单元表与平面图数量对不上怎么办？** ✅ 已解答 — **权威口径 = 44 户**（GROUND 8 + L1 11 + L2 11 + L3 11 + L4 3，另加 2 处 CO-LIVING 集体区， 空间总数 46）。

早前流传的三个口径均已查明来源，**全部作废**：

| 旧口径 | 真实来源 | 为什么错|
|--------|---------|--------|
| **28** | 平面图`UNIT n` 连续序号的最大值 | `UNIT n` 是全楼连续序号，不是户数 |
| **32** | 早期正则统计 | 漏了 GROUND 8 户，且每层漏110/111 |
| **38** | 更早一轮统计 | 同上，且额外漏算 GROUND |

**44 由三重独立证据锁定：**

1. **A008 单元表**：GROUND `G01`–`G08` + `CLA1`；L1 `101`–`111`；L2 `201`–`211`；L3 `301`–`311`；L4 `401`–`403` + `CLA2` → 44 户 + 2 collective
2. **封面 ROOM MIX**：`43 DOUBLE ROOMS + 1 SINGLE ROOM + 2 COMMUNAL LIVING AREA` = 44 户
3. **`MIN DRY AREA: SINGLE ROOM 12SQM, DOUBLE ROOM 16SQM` 规则**：仅 GROUND `G01` 的 DRY = 12.18m² < 16m² → 全楼唯一 SINGLE；其余 43 户均 ≥ 16m² → 恰好对上「43 DOUBLE + 1 SINGLE」

**实测还发现三套编号体系并存**（原报告只预判了两套）：

- L1–L4 数字编码：`101` / `110` / `201` …
- GROUND 字母编码：`G01`–`G08`（完全不用数字）
- CO-LIVING 集体区：`CLA1`（GROUND）/ `CLA2`（LEVEL 4）

> **系统处理方式：** 实现**双数据源逐户交叉验证**而非静默取最大值 ——
> 平面图坐标法解析（主信号）× A008 单元表（最硬证据），两侧逐户对账，
> 只有`verdict=AGREE` 才判通过。当前结果：一致率 `1.0`、面积矛盾 `0` 条、
> 仅平面图 `0`、仅单元表 `0`。差异会显式呈现在 UI 的「溯源诊断」页交由人工裁决。
