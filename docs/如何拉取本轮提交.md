## 按《WorkBuddy 渲染修复需求文档》恢复 DWG 原样导出

需求文档（用户 2026-10-10  提供）核心是「**整体原样导出**」：
不拆元件、不重新排布，把 DWG 里每个柜（含内部全部 water / gas 表）
按识别出的边界框原样渲染成图，保持线条、颜色、尺寸标注不变。

本轮只改 `backend/app/parsers/cupboard_render.py`，
**没动** `cupboard_geometry.py` / `cupboard_classify.py`（需求明确要求别动）。

### 挖出并修掉的 4 个 bug

四个都是「代码看着对、跑起来静默丢东西」的类型 ——
靠读代码看不出来，必须用真实 DWG 渲出来量像素才能抓到。

| # | 现象 | 真根因 | 修法 |
|---|---|---|---|
| ① | 尺寸标注全丢 | `RENDER_TEXT=False`。旧注释断言「系统缺字体」，**实测字体一直可用**（`DejaVuSans.ttf`，330 条缓存）。真因是克隆到 `ezdxf.new()` 临时文档时**没搬 textstyle 表**，DIMENSION 展开的虚拟 MTEXT 带 `style='trebuchet_MS'` 查不到定义 → ezdxf 把 `None` 喂给 `find_font_file_name` 炸掉 | 新增 `_clone_styles()` 搬样式表；`RENDER_TEXT` 改回 `True` |
| ② | 柜内水表整块消失 | `water meter h` 块定义里含 `INSERT 'h-meter'` —— 水表本体是**第二层块**。旧代码只搬一层，`h-meter` 建不出来，ezdxf 渲染时**静默跳过**，5 个水表全没了，而 `entity_count` 仍是 42，看着一切正常 | 新增 `_collect_block_refs()` / `_clone_block_deep()`递归搬运（深度上限 8） |
| ③ | 颜色全被洗掉 | 三处独立失色：a) `color_policy` 硬编码 `BLACK`；b) 顶层实体的图层（`1CO` / `2CONC`）只在 modelspace 出现，**从没搬过**；c) `_trim_white_border` 用灰度图求 bbox 后把**灰度图存回**，裁前彩色 5.04% → 裁后 **0.00%** | 改 `ColorPolicy.COLOR`；新增 `_clone_layers()` 且顶层实体也搬；裁剪改为「灰度图只求 bbox、裁剪用原彩色图」 |
| ④ | SOLID HATCH 变实心块 | 需求「步骤2」点名的项。`water meter h` 块内有 4 个 `pattern_name='SOLID'` + `solid_fill=1` 的 HATCH（CAD 里是阀体底纹），渲出来是一块块黑色实心色块 —— 这正是用户最早报的「黑色实心块」 | 新增 `_demote_solid_hatch()`：`solid_fill=0` + 换 `ANSI31` 剖面线，只描边不填充 |

### 顺带修正的两处误诊

旧注释里两个结论都是错的，本轮更正：

1. **「彩色版线条丢失，因为 ACI 色在白底上太浅」** —— 实测 `ColorPolicy.COLOR`
   在白底工作正常（青/绿/红全出，ACI 7 自动翻黑）。当时字节数低是因为
   **根本没开文字**，图上只剩纯线条。
2. **「`FontFace().filename` 默认 None，style 为空的实体会炸」** ——
   真实 DIMENSION 的虚拟 MTEXT 带的是 `trebuchet_MS`，**不是空串**，
   而且 `get_font_face('trebuchet_MS')` 是能返回 `DejaVuSans.ttf` 的。

### 一个值得记住的 ezdxf 陷阱

```python
dst = doc.layers.get(name) or doc.layers.new(name)   # ❌ 惯用写法在这里是错的
```

`layers.get()` 找不到条目时**抛 `DXFTableEntryError`**（不是返回 `None`），
惯用写法会在抛异常处走人，`new()` 根本执行不到，图层定义永远建不出来。
而 `blocks.get()` 返回 `None`，`or` 短路正常工作 —— **两者行为不一致**。
本轮踩了这个坑两次（图层 + 块），已写成测试
`test_dxf_table_lookup_semantics_differ` 钉住。
