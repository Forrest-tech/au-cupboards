01需求还原：这个系统到底要做什么

去掉建筑行业的包装，这套系统的本质是一个 「图纸 → 计量柜选型清单」的两段式自动化流水线，中间夹着一个可人工干预的确认环节。

STAGE 1
图纸 → 数字模型
上传建筑/户型图（DWG、PDF、Word、JPG）→ 自动识别楼层数与每层 units 数量
STAGE 2
库表 → 选型匹配
按每层 units 数，到「计量柜库」中匹配所有可用的柜体排布方案（1 种 / 2 种 / 3 种…）
STAGE 3
生成清单 → 导出
按楼层按行输出：units 数 → 候选柜型 → 尺寸 → 描述，可导出 PDF / Word / JPG

三个功能区（对应需求 1 / 2 / 3）

模块核心交互本质
A. 主工作台
主界面		 左侧树状导航 + 右侧工作区再分左右两栏：左栏原样预览原始文档，右栏按楼层逐行展示选型结果 典型主从式（Master–Detail）布局 + 文档预览器 + 可编辑数据网格（可排序/分组/增删改）
B. 计量柜库入库
顶部导航		 上传 DWG → 点击「解析」→ 先出分解预览 → 用户确认 → 入库 → 左按表计数量分类 / 右按排布形式展开（尺寸、介绍），支持编辑与删除 本质是「批量导入 + 人工校对（human-in-the-loop）」的字典编辑器。预览确认这一步是需求里写得最正确的设计
C. Building 管理
顶部导航		 上传建筑图纸（PDF 为主 + Word / JPG / DWG）→ 预览 → 选择挂载到树的哪个节点 → 自动解析楼层数与每层 units 与模块 A 共用同一棵树、同一套预览器，不重复造轮子
✅ 需求里写得最好的两个决定

1）模块 B 的「解析 → 预览 → 确认 → 入库」四步走。这正是业界成熟做法。CAD 图纸解析不可能一次到位，把人工确认放在入库之前，而不是之后返工，是正确的流程设计。
2）模块 A 与 C 共用一棵树。避免了「楼栋文档」和「柜型库」割裂成两个孤岛，也避免重复实现导航。

02柜型库 DWG 实图分析（新增 · 关键可行性证据）

你补充了 Cold and hot water and gs meter cupboards detail 1.dwg 在 AutoCAD 2024 中的实际截图。放大分析后，这张图显著改变了几个技术判断——好消息远多于坏消息。

2.1 从图中读到的确定事实

观察项图中证据对系统的意义
柜型以「矩形柜体 + 内部分格」构成 青色矩形 = 柜体外轮廓；内部红色矩形 = 每个表位的独立框；左上柜型为 2 列 × 3 行 = 6 个表位 柜体识别可纯几何化：找闭合矩形轮廓 → 数内部子矩形个数 = 表位数。这不需要 AI，规则引擎即可 100% 准确完成
water / gas 表符号是独立可识别图元 每个表位内是白色管件+绿色表头的标准符号；红色框 = gas 表，绿色竖线元素 = water 表管路 water/gas 计数可按图层 + 块名规则精确提取。这直接回答了报告 Q1 的歧义——图纸本身就带语义，不需要推断
尺寸标注完整存在 左侧柜宽标注链：50 / 175 / 200 / 100 / 250 / 175 / 50，总宽 1000；右上柜标注 50/150/400/150/400/150/400，总高 2200、总宽 1315；下方柜标注 50/120/130/50/400/100/150/100/150/50，总宽 1300 柜体尺寸可直接从 DWG 的 DIMENSION 实体读取，无需按规范反算。报告 Q10 的答案是：读图纸标注，规范公式仅作校验
柜型是多排布并列，而非多文件 同一张图内可见 5 个以上独立柜型（上方 2 个大柜 + 下方 3 个），每个下方都有一行细分格尺寸标注 证实 Q3 的答案是「一个 DWG 内用不同 block/区域表示所有柜型」。入库解析需按空间聚类切分柜型，而非遍历文件
命令行出现 CAMS 命令 命令行显示 Command: CAMS 及后续 CAMS>>> 交互提示 ⚠️ 疑似已有 AutoCAD 插件/脚本在做这件事（CAMS = 可能为 Cabinet And Meter System 之类）。必须查清——若已存在，LISP/ARX 源码可直接复用或移植，能省掉整个 STAGE 2 的解析工作
存在多个同底图的小图 底部三个小图尺寸链各不相同（约 1300 / 不同分段） 说明柜型库按不同 units 数分组组织，正是需求里「7 套 water+gas 有 4 种排布形式」的载体
✅ 重大利好：「100% 识别」这个死结，在柜型库这一侧基本解开了

报告 03 节判定「100% 识别不可兑现」，那个判断只对建筑平面图成立，对柜型库 DWG 不成立。理由：柜型是规则几何图形，有闭合矩形轮廓、有子矩形分格、有图层与颜色区分、有 DIMENSION 标注——全都有确定的几何/语义锚点，不需要靠视觉猜。

这意味着 模块 B（柜型入库 + 匹配）的准确率可以做得很高，而真正的不确定性只集中在 STAGE 1（从建筑平面图推断每层 units 数）。项目的风险分布比原判断乐观得多——建议把解析优先级从「建筑图 AI 识别」转移到「柜型库几何解析」，后者才是第一天就能拿出成果的部分。

🔎 必须立刻查清的一件事：CAMS 是什么

截图命令行里 CAMS 是一个自定义命令（其后有交互式追问，形态像 LISP 的 (defun c:CAMS ...) 或 AutoLISP 命令）。如果这是你或团队已经写好的插件，那么「DWG 解析」这件事你已经有现成实现了——系统只需读取它的输出（实体表 / 属性字典 / 甚至导出 Excel/CSV），而不是从头做几何解析。

请提供：该 CAMS 命令的 LISP 源码或插件文件，以及它能输出什么（CAD 图元 / 文字标注 / 表格 / 数据库）。这可能把 P4 阶段从 10–14 人日降到 2–3 人日。

2.2 修订后的解析策略（因这张图而改变）

❌ 原方案：AI 视觉识别
把柜型图渲染成图片，用视觉模型数格子。精度不可控、不可复现、无法解释。既有的架构分析中，柜型库这一侧也是按「图形聚类 + 人工校对」估算的
✅ 新方案：纯几何 + 语义解析
在 DWG 实体层面直接解析：① 闭合多段线/LWPOLYLINE → 柜体外轮廓；② 其内闭合矩形 → 表位框，数量即 units；③ 按图层/块名区分 gas 表与 water 表；④ 读取 DIMENSION 实体 → 精确尺寸
🔧 建议的数据模型调整：柜型增加「几何特征」字段

既然柜型可被完整几何描述，CupboardVariant 应新增一组可直接用于匹配与排版的字段：

layout_rows        : int     排布行数（如 3）
layout_cols        : int     排布列数（如 2）
positions_total    : int     表位总数（= units 数，如 6）
grid_aspect        : string  "2x3" / "1x7" / "2x2+3"
meter_spacing_h/v  : float   表位间距（从标注读出）
w / h / d (mm)     : float   柜体总尺寸（从 DIMENSION 读出，非手填）
bbox {x,y,w,h}     : float   原图定位，可回溯 DWG 坐标
source_sheet       : string  来源图号/布局名

有了 layout_rows/cols，需求里说的「每层 6 units → 3 种排布」就变成了可枚举、可穷举的匹配问题，而不是模糊判断。

2.3 「DWG 无法上传给我」的影响与应对

需要先厘清一个容易混淆的点：系统最终是在你自己的电脑上运行的，DWG 永远不需要传给我。它传不到我手上，只影响一件事——我无法在写代码前用真实文件验证几何解析规则。

维度是否受影响说明
系统能否解析真实 DWG✅ 不受影响系统在用户机器上运行，读取的是本地文件。这是产品功能，不是开发依赖
能否交付可用的柜型库功能✅ 不受影响柜型库由用户在系统中上传 DWG 触发入库，流程不变
能否提前验证解析规则❌ 受影响我只能从截图推断规则，无法确认不同柜型的边界是否有例外、是否有其他画法
工期估算的可靠性⚠️ 略微受影响P4 的 6–10 人日基于截图推断，实际可能 ±30%。首次跑真实文件时可能需要一轮规则调优
⚠️ 这个约束带来的唯一实质风险：规则可能是「过拟合到这一张图」

我看到的只是一张截图里的 2 个大柜 + 3 个小柜。真实 DWG 里可能有：非矩形柜体、异形表位、嵌套块、跨图框的柜型、不同标注体系（有的标 mm 有的标 m）。如果我把规则写死成「找闭合矩形 + 数内部矩形」，遇到例外图纸就会静默出错。

应对：把解析器做成「规则可配置 + 首次运行有诊断输出」——具体见下方 2.4 的设计约束。

2.4 因此对实现的三条硬约束

① 解析规则必须外置为配置
图层名、颜色、识别阈值、闭合判定容差全部放进 config 文件，不硬编码。用户遇到例外时改配置即可，无需改代码、无需找你
② 必须有「诊断模式」
首次解析时输出诊断报告：识别到几个柜体、各识别到几个表位、哪些图元未被归类、置信度分布。让你（或用户）一眼看出哪里没对上，而不是拿到一堆错数据
③ 修正字典是必需品，不是加分项
用户每次手工修正块名↔表位数、图层↔表类型的对应关系，系统自动记住。这是没有真实样本时唯一能保证准确率的机制
💡 反过来看，这其实让「预览→确认」的价值更大了

原本「预览确认」是为了减少返工。现在它多了一层意义：它是让系统在没有预置知识的情况下自我校准的唯一手段。用户在预览界面改几个框，系统下次就认得了 —— 第一个用这套系统的人，付出的是校准成本，之后所有人享受的是校准后的准确率。这也符合你需求里「用户确认后入库」的原意，只是它的作用比原先更大。

03可行性裁决：「100% 识别 DWG/PDF/JPG，不能有解析问题」

这是需求第 3 条，也是整个项目唯一会导致项目失败的一条。必须在这里把话说清楚。

结论：这条要求在工程上无法兑现，必须改写

不存在任何商业软件或开源库能对任意来源、任意版本、任意画法的建筑图纸做到 100% 无损解析。这不是水平问题，是信息论层面的限制：DWG 是 Autodesk 未公开的私有二进制格式；一份图纸里的「哪条线是墙、哪个块是一套表计」没有任何强制标注标准——图层名叫 0、图层1 还是 WALL-FINAL，全凭设计院习惯。行业公开的工程实践共识是：受控任务上 AI 视觉 85–95%，复杂图纸更低，且必须人工验证。

各格式的真实解析难度

格式可行性真实情况应对策略
DWG 最难 私有闭源格式。新版本支持最好的只有 ODA（Open Design Alliance）——File Converter 免费但需注册，SDK 收费。LibreDWG 开源免费（GPLv3），但对高版本 DWG 支持不全、代理实体/自定义对象会丢失 ODA Converter 转 DXF → ezdxf 解析；LibreDWG 作兜底；关键：解析后校验代理实体是否转空，转空的必须告警
DXF 易 开放格式，ezdxf（MIT）完整支持 R12 → 最新版本，几何/图层/块/标注齐全 直接解析，无需转换
矢量 PDF 易
实测已验证		 pdfplumber/PyMuPDF 可直接抽出矢量文字与坐标。这是最可靠的非 DWG 路径——表计数量往往就写在文字里。✅ 已在74 KEELER ST 实测确认：1.57 MB 完整文本层可抽，UNIT 标注直接可读（见 04 章） 优先抽矢量文字层（找 UNIT n / Apt 201 / Type A 等标注），比看图更准更快。⚠ 但实测发现"抽得到 ≠ 抽得全"，必须加缺号检测与置信度分诊
扫描 PDF / JPG 最难 纯位图。OCR 对小字、旋转文字、密集线网不可靠；只能走视觉大模型，精度受分辨率与图面质量制约 ≥200 DPI 渲染 → 视觉模型结构化抽取 → 强制人工确认，绝不直接入库
Word 中等 可解析，但基本只承载文字/表格/图片，拿不到几何信息 仅作为「单元数清单」的合法来源（很多项目确实用 Word 表格列 units），不做图形识别

建议的改写：从「100% 自动」改为「自动初稿 + 置信度 + 人工确认」

① 每条解析结果带置信度
矢量文字命中=高置信；几何规则命中=中；视觉模型=低。低置信项在 UI 上高亮，要求人工裁定
② 人工修正沉淀为规则字典
每次人工改判都记录下来（"这个块名 = 4 套 water+gas"），系统越用越准。这是真正的技术护城河，也是唯一能逼近 100% 的路径
③ 设「不可信」状态而非静默通过
解析不出来的楼层标为待处理，绝不猜一个数字填进去。工程数据里，一个错数字的代价远大于一个空格子

参考依据：调研中找到的同类商业产品 BuildPass（澳洲本地） 的「AI Floor Plan Scanner」做的正是这件事——上传 PDF 平面图，自动抽出 levels 和 rooms，然后强制用户 review / rename / remove 后再 import。它的产品形态本身就是对这个需求最好的回答。

✅ 补充：这条裁决已被真实图纸实测验证（见 04 章）

04 章对 74 KEELER ST（35 页 A3 建筑图）的实测结果支持这个改写方案：矢量文本抽取确实可行且质量很高（不需要 AI 视觉），但确实会漏数（有缺号的楼层抽不全）。这正好说明——问题从来不是"能不能抽"，而是"抽得全不全"，而"抽得全不全"只能靠置信度 + 人工确认来保障，不能靠算法保证 100%。本裁决在实测后依然成立，且更有说服力了。

规律非常清晰：连续编号被完整抓到（8-11、15-18 都是连号），但编号有断号的楼层就漏。例如 LEVEL 1 抓到 8,9,10,11 是连号所以全中；而 GROUND 只抓到 2,3,3 就说明 UNIT 1 和 5+ 的标注文本没被提取到。

换句话说：「抓到几个编号」≠「这一层有几户」。如果系统只靠数文本标注，会给出偏少的错误数字 —— 这在工程数据里是不可接受的，因为它看起来是个合理的数字，不容易被发现。

4.3 意外发现：粉色填充 = 单元轮廓，但只在 A008 上

我在 A008 UNIT SCHEDULE 页发现每层都有一张缩略平面图，每个独立单元用粉色实心填充。实测该填充色为 RGB(255, 191, 191) / #FFBFBF。这本来是最理想的识别信号，但：

位置粉色填充说明
A008 UNIT SCHEDULE✅ 有每层一张缩略图，粉色块 = 一个单元。这是户数的权威视觉来源
A102~A106 正式平面图❌ 没有实测粉色像素占比 0.00%，正式平面图里根本没有粉色
PDF 对象层❌ 不可提取pdfplumber 只能取到灰/白/蓝填充；粉色不在标准 RGB 空间，疑似 ICC/CMYK 色彩空间定义
💡 结论：粉色是「可靠的交叉验证信号」，但不能作为主路径

粉色填充无法从 PDF 对象层直接提取（需先渲染成位图才能取色），所以不应作为主识别路径。但它可以作为一个高置信度的交叉校验源：当文本解析给出「LEVEL 1 = 4 户」而粉色连通域给出「12 个」时，系统应当自动标记为低置信度并弹窗提示用户复核 —— 而不是默默输出 4。

这正是「多信号交叉验证 + 置信度」机制的真实价值，现在有了具体实现路径。

4.4 两套编号体系并存 —— 必须显式处理

来源编号样式实测样例问题
平面图（A102~A106）连续序号UNIT 2, 3, 4 / 8,9,10,11 / 28同一层内唯一，但跨层不连续（GROUND 是 1-7，LEVEL 1 是 8-14…）

文本层抓取两套都出现了：101/201/301/401（表格）与 UNIT 8（平面图）
🔧 数据模型必须支持「编号体系」抽象

不能把 unit number 存成单一字符串。建议拆成：

Unit
  ├─ label          : "UNIT 8"          图上原始标注（照存，不解释）
  ├─ label_scheme   : "sequential" | "floor_encoded"
  ├─ seq            : 8                  连续序号（sequential 体系）
  ├─ floor_code     : 101                楼层编码（floor_encoded 体系，如 101/201/301）
  ├─ floor_ref      : → Floor (L1)       归属楼层
  └─ confidence     : 0.0~1.0            抽取置信度

关键设计：floor_code 的首位可作为楼层归属的强信号（2xx → LEVEL 2）。当两套体系同时存在时，系统可以互相校验：若 UNIT 28 出现在 LEVEL 4 平面图，而 schedule 表里 4xx 有 3 户但平面图只抓到 1 个 UNIT 标注 → 触发低置信告警。

✅ 重要旁证：两个独立来源得出同一个结论

06 章的 AECV-Bench 实测结论是「视觉模型数符号不可靠，最强只有 40–54%，必须走文字/几何规则」。而 OpenTakeoff 这个 2026 年 7 月的最新开源实现，在「自动识别房间/单元」上选择的也不是视觉模型，而是基于填充图案的连通域填充（flood fill）—— 也就是几何算法。

两个来源、方法完全不同、结论一致：建筑图纸的自动计数应走几何与文本规则，AI 视觉只做兜底和异常提示。这条交叉验证显著提升了我方技术路线的置信度，也说明我们方案里「粉色连通域分析」的方向是对的。

6.1 核心数据：AI 在建筑图纸上的真实精度（AECV-Bench 2026）

⚠ 这是本次调研最重要的发现，直接决定架构走向

AECV-Bench（UNSW 出品，2026年 6 月更新，12 个模型）专门测多模态模型在真实建筑/工程图纸上的能力，结论非常清晰：模型「读得懂文字」但「数不准东西」。

• OCR / 文字抽取 ≈ 95–98%（房间名、尺寸标注、注释）—— 很强
• 符号计数（数门/数窗/数卧室/数厕所）= 40–54% —— 不可用
• 空间推理 = 0.54–0.88 —— 中等，且模型间差异大

对本项目的直接含义：「每层有几个 unit」本质上是符号计数问题。直接问AI「这层有几套单元」会得到 40–50% 正确率 —— 在工程数据里这是灾难性的，因为它会给出一个看起来合理的错误数字。所以 AI 绝不能作为 STAGE 1 的主路径，这与 04 章实测「纯文本抽取才是正道」完全一致，互为印证。

6.4 关键判断：STAGE 1 的准确度其实不依赖 AI

✅ 准确度的真正来源（回应「需要保证准确度」的核心诉求）

需求方最关心「保证准确度」。结合本次调研，准确度的来源按贡献排序是：

  1. 矢量文本层（免费，95–98%） —— 主路径。UNIT 标注、房间名、尺寸链都有文字锚点，可靠。这是准确度的主要贡献者。
  2. 缺号检测 + 交叉验证（免费，100% 可靠） —— 这是本系统的核心创新。04 章实测「文本抽全会漏数」，而 A008 粉色连通域 + 单元表floor_code + 封面声明可以互相校验。三信号不一致就强制人工确认—— 这比任何 AI 都可靠，因为它不猜测。
  3. A008 粉色填充位图分析（免费，90%+） —— 仅在 A008 页面运行，作为户数权威视觉来源。
  4. VLM API（付费，40–54% 计数） —— 仅用于无文本层扫描件的兜底，且强制人工确认。不指望它做主要识别。
  5. 修正字典（免费，越用越准） —— 每次人工改判沉淀为规则，系统自我校准。复利资产。

结论：准确度不来自「更强的 AI」，而来自「多信号交叉验证 + 人工兜底 + 自我校准」的机制设计。这正是 BuildPass（澳洲同类产品）验证过的产品形态—— AI 出初稿 + 人工 review 后入库，而不是「AI 全自动」。

🔑 数据模型里最关键的两个设计

10核心难点与解法（按难度排序）

最难 每层 units 数量识别 ← 唯一真难点（已实测，见 04）
已在真实图纸（74 KEELER ST，35 页）上实测：矢量文本层完整可抽，UNIT 标注能直接读到，但会漏数——连续编号段抽全、有缺号的楼层漏抽（LEVEL 4 只读到 1 间）。解法是三路信号交叉验证：① 文本 UNIT 编号连续性 ② 房间关键词计数 ③ 粉红填充连通域（仅 A008 有）。柜型库侧的几何确定性无法复用到建筑平面图——建筑图没有闭合矩形网格
最难 DWG 代理实体丢失
第三方插件生成的图元转 DXF 后可能变空。必须做转换后完整性校验：转换前后实体数/块数对比，差异超阈值直接告警而不是静默通过。注：74 KEELER ST 是 PDF 出图，无此风险；风险来自建筑 DWG
已降级 柜型自动分解入库 （原「较难」）
从截图看柜体是规则闭合矩形 + 内部子矩形分格，几何解析即可，不必用 AI。数子矩形个数 = units 数，按图层区分 water/gas，读取 DIMENSION 取尺寸。风险大幅下降
已降级 选型匹配算法 （原「中等」）
有了 layout_rows/cols/positions_total，匹配变成有限组合穷举：某层 units=N → 找出所有满足 positions_total=N 的柜型（含 2×N1+N2 组合）。纯查表，无歧义
已降级 楼层顺序与命名 （原「较难」）
实测遇到的命名是 BASEMENT / GROUND / LEVEL 1–4 / ROOF——已是主流规范，归一化映射表一次写对即可。真正要处理的只有地下层无 units 的跳过规则
中等 原样预览一致性
需求强调"原样显示"。CAD 图纸存在字体缺失（SHX）、线型缺失问题，需做字体映射表与线型兜底，否则预览与原图不符。PDF 侧实测无此问题（Archicad 出图，字体已嵌入）
中等 两套编号体系并存 新增
平面图用连续序号（2–28），A008 单元表用楼层编码（101/201/301/401）。不能混为一谈，需在 Unit 模型里分开存 seq 与 floor_code，并以图号（A102→LEVEL 1）作为楼层锚点做交叉校验
中等 多图纸集与多比例 新增
单项目 PDF 常有 30+ 张图、混合 A3/A4 比例、含封面/目录/透视图。必须靠图号前缀（A1xx 平面 / A3xx 立面 / A4xx 剖面）过滤，否则会把立面图上的"层号"误当楼层

13待澄清问题（开工前必须确认）

Q1「units」到底指什么？已基本解答
从柜型库截图看，一个表位 = 1 套 water + gas（冷热双表 + 1 气表），所以在这套库里 units ≈ 表位数。真实图纸实测进一步支持这个口径：每个 UNIT 标注对应一套独立计量柜位，单元表（A008）的表位数与平面图上的 UNIT 数应当一一对应。

剩余唯一需你确认的：① 图纸封面上除 43 套 double + 1 套 single 之外，还有 2 处 CO-LIVING communal 共享区（S34）——这些是否也要配柜、是否计入 units？② 是否有「1 个 unit 配 2 个柜位」或「2 个 unit 共享 1 套表」的情况？
Q2每层的 units 数据来源是什么图？已解答
已确认为建筑平面图，且实测给出了完整答案。来源与信号如下：

① 主路径 — A1xx 平面图上的 UNIT n 文字标注。74 KEELER ST 里 LEVEL 1 图上清晰可读 UNIT 8 / 9 / 10 / 11，同页还有 ND.76-72 KEELER ST 可作地址锚点。矢量文本层完整可抽（pdftotext -layout 抽出 1.57 MB 文本），无需 AI。
② 辅助 — A008 单元表（专有粉红填充标每套单元），是全项目里唯一的"按单元着色"页面。
③ 校验 — 房间关键词计数（KITCHEN / LIVING / BED / BATH / BALCONY 等）。

⚠ 实测发现的坑：单靠文本会漏数。连续编号段能抽全，但有缺号的楼层会漏（LEVEL 4 只读到 1 间）。所以不能只做文本抽取，必须做三信号交叉验证 + 置信度分诊（详见 4.2 / 4.5）。
Q2b单元表与平面图数量对不上怎么办？已解答
权威口径 = 44 户（GROUND 8 + L1 11 + L2 11 + L3 11 + L4 3，另加 2 处 CO-LIVING 集体区，空间总数 46）。

早前流传的三个口径均已查明来源，全部作废：
旧口径真实来源为什么错
28平面图 UNIT n 连续序号的最大值UNIT n 是全楼连续序号，不是户数
32早期正则统计漏了 GROUND 8 户，且每层漏 110/111
38更早一轮统计同上，且额外漏算 GROUND
44 由三重独立证据锁定：
  1. A008 单元表：GROUND G01–G08 + CLA1；L1 101–111；L2 201–211；L3 301–311；L4 401–403 + CLA2 → 44 户 + 2 collective
  2. 封面 ROOM MIX：43 DOUBLE ROOMS + 1 SINGLE ROOM + 2 COMMUNAL LIVING AREA = 44 户
  3. MIN DRY AREA: SINGLE ROOM 12SQM, DOUBLE ROOM 16SQM 规则：仅 GROUND G01 的 DRY = 12.18m² < 16m² → 全楼唯一 SINGLE；其余 43 户均 ≥ 16m² → 恰好对上「43 DOUBLE + 1 SINGLE」
实测还发现三套编号体系并存（原报告只预判了两套）：L1–L4 数字编码 101/110/201…、GROUND 字母编码 G01–G08（完全不用数字）、CO-LIVING 集体区 CLA1（GROUND）/ CLA2（LEVEL 4）。

系统处理方式：实现双数据源逐户交叉验证而非静默取最大值 —— 平面图坐标法解析（主信号）× A008 单元表（最硬证据），两侧逐户对账，只有 verdict=AGREE 才判通过。当前结果：一致率 1.0、面积矛盾 0 条、仅平面图 0、仅单元表 0。
